# Q&A 작성 페이지 R2 버킷 구조 검토

## 1. 검토 배경

정적 홈페이지와 Q&A 작성 페이지를 분리한다.

- 홈페이지 정적 파일: 기존 홈페이지 버킷
- Q&A 작성 페이지: 홈페이지와 별도의 R2 버킷
- Q&A 대상 서비스: EGBIM, TOVA, GAIA
- 각 서비스의 운영 주체와 외부 관리 API가 서로 다름
- SSO/IdP는 공통으로 사용할 수 있음
- 작성 내용, DB, 첨부파일 저장은 각 외부 관리 서버가 담당

이 문서는 Q&A 작성 페이지 전용 버킷을 하나로 운영할지, 서비스별로 분리할지 비교한다.

## 2. 전제 아키텍처

Q&A 작성 페이지는 R2에 정적 HTML/CSS/JS를 저장하고 Worker를 통해 서비스한다.
작성 요청은 브라우저에서 각 서비스의 외부 관리 API로 전송한다.

```text
사용자
  ├─ 홈페이지 정적 페이지
  │    └─ 공통 SSO 로그인
  │
  └─ Q&A 작성 페이지
       ├─ 공통 SSO 세션 재사용
       ├─ 서비스별 작성 화면
       └─ 서비스별 외부 관리 API 호출
             └─ 서비스별 DB / 첨부파일 저장소
```

R2는 작성 데이터나 DB를 저장하는 장소가 아니라 작성 페이지 정적 파일을 제공하는 저장소로 사용한다.

## 3. 안 A: Q&A 작성 페이지 전용 버킷 하나

예시:

```text
baron-qa-pages/
├── egbim/
├── tova/
└── gaia/
```

R2는 실제 폴더가 아니라 object key prefix로 파일을 그룹화한다. 따라서 제품별 prefix로 정적 파일을 구분할 수 있다.

### 장점

- Worker와 R2 binding을 하나만 관리하면 된다.
- 공통 로그인 화면, 폰트, CSS, JS를 재사용하기 쉽다.
- 배포 workflow와 모니터링 구성이 단순하다.
- 새로운 서비스 추가 시 prefix와 페이지를 추가하면 된다.
- 서비스별 버킷을 여러 개 생성하고 관리하는 운영 부담이 적다.

### 단점

- 한 버킷에 대한 Worker binding은 기본적으로 버킷 전체에 접근할 수 있다.
- prefix는 파일 정리 기준이지 강한 권한 분리 경계가 아니다.
- 잘못된 `--delete` 배포나 경로 설정으로 다른 서비스 파일에 영향을 줄 수 있다.
- 서비스별 운영 주체에게 R2 직접 권한을 줄 경우 다른 서비스 파일까지 보일 수 있다.
- 서비스별 독립 배포, 롤백, 보존 정책을 적용하기 어렵다.

### 적합한 경우

- 중앙팀이 모든 Q&A 페이지를 배포한다.
- 각 운영 주체는 R2에 직접 접근하지 않고 API만 운영한다.
- 정적 페이지의 배포 주기와 보안 정책이 거의 같다.
- 장애 영향 범위를 공유해도 문제가 없다.

## 4. 안 B: 서비스별 버킷 분리

예시:

```text
baron-qa-egbim
baron-qa-tova
baron-qa-gaia
```

각 버킷은 해당 서비스의 Worker 또는 서비스별 Worker 환경에만 연결한다.

### 장점

- 서비스별 파일과 배포 범위가 물리적으로 분리된다.
- 한 서비스의 삭제, 배포 실수, 파일 손상이 다른 서비스에 영향을 주지 않는다.
- 운영 주체별 R2 권한을 최소화하기 쉽다.
- 서비스별 독립 배포와 롤백이 쉽다.
- 서비스별 보존 기간, 접근 정책, 장애 대응을 따로 적용할 수 있다.
- API와 정적 페이지의 소유 관계가 명확해진다.

### 단점

- 버킷, Worker binding, workflow, 모니터링 구성이 늘어난다.
- 공통 자산을 공유하려면 별도 공통 버킷이나 중복 배포가 필요하다.
- 서비스 추가 때마다 인프라 설정이 추가된다.
- 운영자가 여러 버킷의 상태와 배포 결과를 확인해야 한다.
- 공통 SSO를 사용하더라도 서비스별 Worker 설정을 일관되게 유지해야 한다.

### 적합한 경우

- 서비스별 운영 주체가 서로 다르다.
- 서비스별 API와 DB가 서로 다른 권한 체계를 사용한다.
- 운영 주체가 각자 배포하거나 파일을 관리해야 한다.
- 서비스별 장애 격리와 독립 롤백이 중요하다.
- 향후 서비스별 계약, 보존, 감사 정책이 달라질 수 있다.

## 5. 항목별 비교

| 항목 | Q&A 버킷 하나 | 서비스별 버킷 |
|---|---|---|
| 초기 구축 | 단순함 | 설정이 많음 |
| 운영 주체 분리 | 약함 | 강함 |
| API/DB 분리 | 가능하지만 별도 코드 필요 | 자연스럽게 분리됨 |
| 배포 영향 범위 | 전체 Q&A | 서비스 단위 |
| 권한 최소화 | 어려움 | 쉬움 |
| 공통 자산 재사용 | 쉬움 | 별도 설계 필요 |
| 독립 롤백 | 어려움 | 쉬움 |
| 장애 격리 | 약함 | 강함 |
| 신규 서비스 추가 | prefix 추가 | 버킷/Worker 추가 |
| 운영 복잡도 | 낮음 | 높음 |
| 장기 확장성 | 중앙 관리에 적합 | 조직·서비스 분리에 적합 |

## 6. 보안상 핵심 판단

운영 주체가 다르다는 사실만으로 반드시 버킷을 분리해야 하는 것은 아니다.
각 운영 주체가 외부 API만 관리하고 R2와 Worker 배포 권한을 갖지 않는다면, 하나의 Q&A 버킷도 운영할 수 있다.

반대로 다음 중 하나라도 해당하면 서비스별 버킷이 적합하다.

- 운영 주체가 각자 정적 페이지를 배포한다.
- 서비스별 R2 또는 Worker 권한을 따로 줘야 한다.
- 한 서비스의 배포 실패가 다른 서비스에 영향을 주면 안 된다.
- 서비스별로 독립적인 롤백과 감사 추적이 필요하다.
- 서비스별 API 인증 정책이나 데이터 보존 정책이 다르다.

## 7. 배포 workflow 영향

### 버킷 하나

공통 workflow 하나로 관리할 수 있지만, `--delete`를 사용하는 전체 동기화는 위험하다.
서비스별 prefix를 보존하거나, 제품별 prefix만 배포하도록 제한해야 한다.

```text
deploy egbim -> egbim/만 변경
deploy tova  -> tova/만 변경
deploy gaia  -> gaia/만 변경
```

### 서비스별 버킷

각 workflow가 자신의 버킷만 대상으로 하므로 `--delete`의 영향 범위가 작다.
대신 서비스별 GitHub Secret, Worker binding, 배포 workflow를 관리해야 한다.

## 8. 권장안

현재 조건에서는 **서비스별 버킷 분리**를 권장한다.

이유는 다음과 같다.

1. EGBIM, TOVA, GAIA의 운영 주체가 다르다.
2. 각 서비스가 서로 다른 외부 관리 API와 DB를 사용한다.
3. Q&A 페이지는 홈페이지와 이미 분리된 별도 서비스 경계다.
4. 작성 페이지의 배포 또는 수정 실수가 다른 서비스에 영향을 주지 않아야 한다.
5. 제품별 독립 운영과 향후 권한 분리가 필요할 가능성이 높다.

권장 기본 구조:

```text
홈페이지
  └─ baron-hompage

Q&A 작성 페이지
  ├─ baron-qa-egbim
  ├─ baron-qa-tova
  └─ baron-qa-gaia
```

공통 SSO/IdP는 공유하되, 다음은 서비스별로 분리한다.

- 작성 페이지 정적 파일
- Worker 환경 설정
- 외부 API endpoint
- API 인증·권한 정책
- DB와 첨부파일 저장소
- 배포 workflow와 롤백 단위

## 9. 버킷 하나로 시작할 수 있는 예외

아직 운영 주체가 R2나 Worker에 직접 접근하지 않고, 중앙팀이 모든 배포를 담당한다면 초기에는 `baron-qa-pages` 하나로 시작할 수 있다.

다만 이 경우에도 아래 조건을 지켜야 한다.

- 서비스별 prefix를 강제한다.
- 배포 workflow를 prefix 단위로 제한한다.
- API endpoint와 product 식별자를 서비스별로 고정한다.
- Q&A 버킷과 홈페이지 버킷은 계속 분리한다.
- 운영 주체에 버킷 전체 권한을 부여하지 않는다.

## 10. 최종 결정 체크리스트

다음 질문에 하나라도 `예`라면 서비스별 버킷 분리를 선택한다.

- 각 운영 주체가 직접 배포하거나 파일을 수정하는가?
- 서비스별로 다른 R2/Worker 권한이 필요한가?
- 서비스별 독립 롤백이 필요한가?
- 한 서비스 장애가 다른 서비스에 영향을 주면 안 되는가?
- 서비스별 보존·감사·보안 정책이 달라질 가능성이 있는가?

현재 제공된 조건만 기준으로 보면 이 질문들에 대부분 `예`가 될 가능성이 높으므로, 서비스별 버킷 구조가 장기적으로 더 안전하다.
